## 这一版为何值得写

vLLM 是常用的模型推理服务框架。此版本新增 Mistral Large 4、MiniMax M3.1 Flash 等模型支持。默认分配行为和 GPU 运行器也变了，原先能正常启动的配置需要按发布说明检查。

## 升级时检查什么

项目已移除 GPU Model Runner V1，且默认缓存块大小有调整。建议用现有配置先在测试环境启动，跑一遍长上下文、并发请求和显存占用，再决定是否切换服务。

## 具体改动

- GPU Runner 统一到 V2。设有 `VLLM_USE_V2_MODEL_RUNNER=0` 的启动配置会报错；V1 自定义 logits processor 也需要迁移。
- 可扩展 KV 缓存默认开启，按预热后的空余显存确定容量。多数独占 GPU 的部署可从无自定义显存比例开始测试，共享 GPU 的部署仍要明确分配上限。
- 默认 `--block-size` 由 16 改为 64；ROCm paged attention 仍用 16。停止提供 ROCm 7.2 构建，Python 环境要求 `huggingface_hub>=2.0.0`。新增 Mistral Large 4、MiniMax-M3.1-Flash 和 Nemotron-3.5-Transcribe 等模型支持。

## 缓存为何影响并发

自回归解码会反复使用已有 token 的注意力 K/V，缓存容量决定可以同时保留多少个长请求。v0.34.0 默认在预热后按空余显存规划容量。独占 GPU 的服务可能因此留出更多空间。与其他进程共用 GPU 时，显存预算仍需显式处理并测试峰值。

## 兼容性矩阵

| 部署路径 | 需要核对 |
| --- | --- |
| NVIDIA 容器 | 删除强制旧 Runner 的变量。使用自定义 logits processor 的部署核对 V2 导入路径 |
| AMD 容器 | ROCm 7.2 构建停止发布。ROCm paged attention 的 block size 仍为 16 |
| 自行安装 Python 依赖 | 核对 huggingface_hub、tokenizers 与 timm 的版本要求，避免旧环境掩盖冷启动问题 |
| 客户端与基准 | 对照 16 和 64 的块尺寸，固定同一权重、上下文长度和并发上限 |

## 影响与验证

先跑一份与生产相同的配置验证能否启动，再用短提示词高并发与长提示词低并发两组负载对比可用 KV token 数、P95 首 token 和 OOM。依赖旧 block size 的下游可以显式传 16 作为对照。
